# Ubiquitous Language Glossary

## 使用时机

- 术语存在歧义或同名不同义，导致设计与代码难以对齐。
- 需要把业务语言固化为可审计、可演进的词汇资产。

## 输入要求

- 术语候选与歧义清单（来自阶段 0/1）。
- 限界上下文目录与词汇表骨架（来自阶段 2，如已完成）。
- 现有代码/接口/文档中的核心名词（如有）。

## 流程

1. 合并术语候选，建立“主术语”与“别名/同义词”。  
2. 为每个术语给出简洁定义，并提供 1 个业务示例。  
3. 标注上下文归属：术语在哪个限界上下文内有效。  
4. 识别冲突：同名不同义、近义混用、技术词污染业务词。  
5. 建立反术语（Anti-terms）：禁止用词与替代用词。  
6. 输出演进规则：新增术语流程、变更影响评估、版本记录方式。

## 输出

| 工件 | 结构要求 |
| :--- | :--- |
| 通用语言词汇表 | 表格：术语、定义、示例、上下文、同义词、反术语、冲突处理 |
| 反术语清单 | 表格：禁止用词、问题原因、推荐替代 |
| 演进规则 | 列表：新增/变更流程、评审角色、版本策略 |

## 校验清单

- [ ] 每个术语都有清晰定义与示例
- [ ] 冲突术语都有“上下文归属 + 翻译/替换策略”
- [ ] 反术语清单覆盖技术词污染与含混词（如 Manager、Processor）

## 常见陷阱

- 词汇表只是“名词列表”，缺少定义与示例，无法约束代码。
- 不区分上下文归属，强行统一导致模型扭曲。

## 示例

```text
使用 @ddd-ubiquitous-language-glossary 把“订单/交易/结算/支付”等术语统一为通用语言：
输出词汇表、反术语清单与演进规则。
```
