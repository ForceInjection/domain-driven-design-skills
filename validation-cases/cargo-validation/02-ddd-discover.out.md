# 02 — ddd-discover 产出（Blind Run）

> 输入：`00-fuzzy-prompt.md` + `01-ddd-scope.out.md`。
> 本文件为 `ddd-discover` 在 blind run 下的模拟执行产出，**未参考** `reference/` 下任何真值材料。
> 事件命名采用**过去时**；至少覆盖 1 条主路径 + 2 条异常/回滚路径。

## 事件流表

## 命令候选清单

| 命令                     | 发起者        | 期望结果                       | 幂等性要求                                         |
| :----------------------- | :------------ | :----------------------------- | :------------------------------------------------- |
| `SubmitShippingRequest`  | 客户          | 产生需求编号                   | 以 clientRequestId 幂等                            |
| `QueryRoutingOptions`    | 系统          | 若干候选方案                   | 只读，天然幂等                                     |
| `SelectOption`           | 客户          | 选中方案                       | 以需求编号 + 方案编号幂等                          |
| `ConfirmBooking`         | 订舱员 / 系统 | 产生订单 / 一票货物            | 以需求编号幂等（一单一次）                         |
| `AssignRoute`            | 系统          | 为订单指派一条路线             | 允许覆盖，需版本化                                 |
| `RegisterHandling(type)` | 港口作业方    | 写入一条作业事实               | 以 (订单 + 航段 + 作业类型 + 发生时间 + 港口) 幂等 |
| `RequestReroute`         | 客服 / 系统   | 触发重新规划流程               | 以订单 + 异常版本号幂等                            |

## 热点标注

### 一致性热点

- 作业事实的**判重键**必须稳定：(订单 + 作业类型 + 发生时间 + 港口 + 航段) 的组合需在全系统达成共识，否则同一事实被算多次。
- "错卸 / 应到" 的判定要求**当前路线计划**与**实际作业**在同一时刻可比；涉及路线版本与作业到达顺序的强一致性。
- 迟到数据入库后必须按 `occurredAt` 排序**重算派生状态**（位置 / ETA / 异常）。

### 集成热点

- 与**外部航线提供方**的接口是系统最脆弱的外部边界：必须有防腐层。下单与重规划两处复用，但两处的调用上下文不同（一个基于需求，一个基于当前位置）。
- 与**外部港口作业方**的接口多通道（Web/API/文件）异步不可靠：必须有"吸收+去重+隔离"三段式。

### 性能热点

- 峰值 50 万事件/日，约 **5.8 QPS 平均、峰值估计 50–100 QPS**（短时集中提交）；叠加查询峰值 200 QPS；登记入库必须异步化并分区。
- 客户查询路径（当前位置 / 状态 / ETA / 下一步）是高频读；应从事件派生读模型，禁止实时聚合。

### 合规 / 审计热点

- 作业事实一经写入不可"静默删除"：修正须以新版本事实覆盖并保留审计链。
- 迟到数据的"时间回溯"可能导致历史派生状态被修改，需完整审计。

## 歧义清单

| 歧义点                               | 影响范围             | 需确认方         | 建议决策                                                  |
| :----------------------------------- | :------------------- | :--------------- | :-------------------------------------------------------- |
| "需求" 与 "订单" 是否同一实体？      | 整个下单流程         | 订舱业务负责人   | **拆分**：需求是询价/询方案阶段；订单在客户确认方案后产生 |
| 路线是否可持久化？版本化？           | 作业 / 查询 / 重规划 | 订舱 + 作业      | **版本化持久化**，作业事件引用版本号                      |
| 判重键的具体字段组合                 | 全体作业登记         | 作业数据对接团队 | 以 (订单, 作业类型, 港口, 发生时间, 航段) 为默认键        |
| 错卸由谁判定                         | 异常识别             | 订舱 + 客服      | 由系统基于"已指派路线"自动判定，客服可复核                |
| 重规划是否必须保住原最晚到达时间     | 异常流程             | 业务方           | 尽量保住，不能保住时需客户确认是否接受                    |
| 客户改目的地是否允许？何时截止？     | 全流程               | 订舱 + 法务      | 在某关键事件（如已装船）之前允许；之后需走变更流程        |
| 非目标的计费与本期状态派生是否有耦合 | 范围边界             | 业务方           | 明确：本期完全不触达计费字段                              |
| 外部航线提供方是否会被替换或多源     | 集成策略             | 架构 + 商务      | 按"可替换"设计：防腐层收敛                                |

## 边界线索（供 `ddd-subdomains` / `ddd-contexts` 消费）

基于事件聚类、热点分布、团队划分，初步识别 **4 个能力分组候选**：

1. **订舱能力**（核心）：从托运需求到订单确认，再到路线指派与重指派；拥有"一票货物"的权威状态推导规则。对应团队：订舱/客服团队。
2. **港口作业能力**（支撑但关键）：异步吸收外部作业事实，做幂等、校验、隔离；仅对外暴露"作业事实已接受 / 已拒绝"。对应团队：港口作业数据对接团队。
3. **客户查询能力**（支撑）：面向客户的读模型，组合订舱与作业事实，派生位置/状态/ETA/下一步。对应团队：面向客户的前端团队。
4. **航线规划能力**（通用，外购）：由外部提供方提供可行方案；本系统不自建，只经防腐层调用。

**跨边界关键关系**：

- 订舱 → 港口作业：订舱下发"路线已指派"，作业回馈"作业事实"。
- 订舱 ← 港口作业：异常推导（错卸）由订舱消费作业事实得出。
- 客户查询 ← 订舱 + 港口作业：只读聚合。
- 订舱 ↔ 航线规划：同步请求/响应，防腐层隔离。
