# 00 — Blind Run Fuzzy Prompt

> 本 prompt 用于 blind run：模拟真实业务方提出的模糊需求。**不含任何 DDD 术语**（聚合、上下文、实体、值对象、事件风暴、通用语言等均不得出现）；**不含任何样例代码中的类名/包名**（Cargo、HandlingEvent、Itinerary、Voyage、RouteSpecification、Pathfinder 等均不得出现）。

## 业务背景（来自某国际物流公司的初步沟通纪要）

我们是一家国际海运物流服务商，客户主要是制造业与外贸企业。过去几年业务量翻倍，原有的一套靠邮件 + Excel + 若干零散系统维持的流程已经跟不上，客户投诉与内部扯皮在增加。我们希望搭建一个新系统，把"从客户提出托运需求"到"货物交付客户签收"的全过程串起来。

## 现状痛点

1. **客户下单环节**：客户通常只告诉我们起点、目的地、最晚到达时间。我们的订舱员需要人工到各个船公司网站上查什么船能走、什么时候出港、要不要中转，再回复客户几种可行方案，客户挑一种后我们才算下单成功。这个来回沟通平均要 2~3 天，客户抱怨慢。
2. **港口作业登记**：货物从仓库出来之后会经过多个港口：收货、装船、途中、卸船、转运、最终到港、客户提货。每个港口的作业人员（可能是我们自己的人、可能是外部合作方）会往系统里登记"什么时候、在哪个港口、发生了什么"。目前这些登记数据很乱：有的重复提交、有的字段写得不规范、有的延迟好几天才进来。
3. **异常识别**：有时候货物会被错卸到不该卸的港口（比如本应在纽约中转却被卸到东京）。现在我们发现这类问题基本靠客户打电话投诉，系统自己发现不了。一旦出错，我们需要重新规划一条从当前位置到目的地的新方案，并把客户原本答应的送达时间尽量保住。
4. **客户查询体验**：客户想知道"我的货现在在哪里？接下来要做什么？预计什么时候到？有没有走错？"，现在只能打电话问客服，客服再查各种系统拼答案。
5. **路线规划**：查船期、拼航段的活儿，我们现在用一个外部合作伙伴提供的线上系统（是一家专门做航线数据的公司，不是我们自己开发的）。我们调他们接口，他们返回若干可行方案。这个关系以后还会保持，我们不打算自己搞一套航线数据。

## 期望目标

- 客户能在线提交托运需求（起点、终点、最晚到达时间），系统返回可选方案列表，客户选一个即完成下单。
- 港口作业方能通过 Web/API/文件导入等方式登记作业事实；系统必须能识别重复提交与不合法数据。
- 系统自动识别"走错了"的情况并通知相关人员，支持重新规划路线。
- 客户可以在网站上实时查询自己货物的位置、状态、下一步预期动作、预计到达时间。
- 与外部航线数据提供方保持松耦合，不让他们的改动随便打穿我们的系统。

## 非目标（客户明确说过不在这一期做）

- **不做计费与财务**：走哪条线价格多少、应收多少、开票、对账，这些暂时不做，留到下一期。
- **不做客户 CRM**：客户的联系方式、信用档案、历史对账，不在本系统范围。
- **不做船公司内部调度**：我们不替船公司安排船的班次。
- **不做仓储管理**：货物在仓库里怎么摆、怎么盘点，不在本系统。

## 约束

- 系统必须能够异步吸收外部港口作业数据：对方可能延迟几小时到几天才把事件推过来；我方接收时必须能去重。
- 与外部航线提供方的接口可能随时变，我方不能让他们的字段直接出现在我方的核心模型里。
- 一票货物从下单到交付通常跨越 2~6 周，期间可能会改目的地、改航线、出异常。
- 运营规模：峰值每天下单 5000 票、作业事件 50 万条；峰值 QPS 约 200。
- 团队：订舱/客服团队、港口作业数据对接团队、面向客户的前端团队，各自相对独立。

## 我们希望你帮我们做的

请帮我们把这摊模糊的业务需求，收敛为一个清晰的建模输入：问题到底是什么、范围边界在哪里、核心概念有哪些、主要的业务风险是什么，以及进入下一步建模需要哪些必要信息。
