# DDD Testing Strategy

## 使用时机

- 领域规则复杂但缺少可信测试，改动风险高。
- 需要把测试变成“活文档”，支撑持续演进与重构。

## 输入要求

- 关键用例列表（用例名 + 业务规则）。
- 聚合不变量清单（如已完成）。
- 技术栈信息（Python/.NET/Java）与现有测试框架（如已知）。

## 流程

1. 建立测试分层：领域模型单测、用例/服务层单测、适配器契约测试。  
2. 为每个用例生成测试清单：Happy Path + 边界条件 + 异常路径。  
3. 制定命名规约：`test_{目标}_{场景}_{期望结果}`，要求可读且可搜索。  
4. 定义严格断言策略：所有 DTO 字段、异常信息、Mock 调用、副作用均需验证。  
5. 为跨上下文交互定义契约测试与幂等验证点。  
6. 输出按优先级排序的落地计划：先覆盖核心域与高风险规则。  

## 输出

| 工件 | 结构要求 |
| :--- | :--- |
| 测试分层说明 | 列表：层级、目标、允许依赖、推荐工具 |
| 用例测试清单 | 表格：用例、场景、输入、期望、断言点 |
| 命名与组织规范 | 命名格式、目录建议、禁止事项 |
| 严格验证规则 | DTO 字段断言、异常断言、Mock 验证、副作用验证 |
| 落地优先级 | 表格：模块/用例、风险、优先级、验收方式 |

## 校验清单

- [ ] 核心域用例至少覆盖 1 条 Happy Path 与 2 条异常路径
- [ ] 测试用例包含字段级断言与副作用验证
- [ ] 命名规约统一且可在 CI 中稳定执行

## 常见陷阱

- 只断言“无异常”或只断言“返回非空”，导致测试失去保护作用。
- 领域测试依赖真实数据库/外部 API，运行慢且不稳定。

## 示例

```text
使用 @ddd-testing-strategy 为“下单、支付、退款”三个用例生成测试策略：
输出分层方案、用例测试清单、命名规约与严格断言规则。
```
