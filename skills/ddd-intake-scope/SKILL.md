# DDD Intake & Scope

## 使用时机

- 需求描述较模糊，且不同角色对问题边界理解不一致。
- 需要在 DDD 流程开始前，锁定目标、约束与风险，避免后续反复返工。

## 输入要求

- 业务目标或问题描述（允许是非结构化文本）。
- 业务背景：当前系统形态、关键参与方、外部系统。
- 约束：时间、合规、性能、数据边界、团队结构（如已知）。

## 流程

1. 提取业务意图，形成 1 句“问题陈述”和 1 句“价值陈述”。  
2. 明确目标与非目标，建立范围边界（包含不做什么）。  
3. 列出关键约束与假设，并标注“可验证/不可验证”。  
4. 生成术语候选清单：名词、动词、状态词，并标注歧义点。  
5. 识别风险清单：业务风险、集成风险、数据一致性风险、交付风险，并给出缓解建议。  
6. 输出下一阶段（事件风暴）需要准备的最小信息与参与角色。

## 输出

| 工件 | 结构要求 |
| :--- | :--- |
| 问题陈述与价值陈述 | 各 1 句，可被业务人员认可 |
| 目标 / 非目标 | 列表化，包含边界解释 |
| 约束与假设 | 每条标注“可验证性”与验证方式 |
| 术语候选与歧义 | 表格：术语、定义候选、歧义、所属场景 |
| 风险与缓解 | 表格：风险、影响、触发条件、缓解方案 |
| 下一阶段准备清单 | 参与角色、必要输入、会议产出 |

## 校验清单

- [ ] 目标与非目标互斥且可落地执行
- [ ] 约束与假设已标注验证方式
- [ ] 至少输出 10 个术语候选并识别歧义点
- [ ] 风险清单覆盖业务/集成/一致性/交付四类

## 常见陷阱

- 把“解决方案”当作目标，导致后续建模被技术细节牵引。
- 非目标缺失，范围持续漂移。
- 术语未记录歧义来源，后续出现“同词不同义”。

## 示例

```text
使用 @ddd-intake-scope 帮我把“订单售后很乱、跨系统协同困难”的问题收敛为 DDD 建模输入：
输出目标/非目标、约束与假设、术语候选表、风险清单与下一步事件风暴准备清单。
```
