# 领域驱动设计技能调研报告

> 🌐 English version: [English](ddd-skills-report.en.md)

本文档系统性地梳理了开源生态及本地预置资源库中的领域驱动设计相关人工智能技能。通过深度剖析各技能的底层逻辑、规则约束与实际执行路径，旨在为开发团队在复杂业务建模、系统边界划分以及多语言战术代码落地时，提供精准的智能化辅助工具选型与架构决策参考。

---

## 1. 战略规划与架构设计类

战略规划阶段是领域驱动设计的核心起点。利用事件风暴、领域划分与上下文映射等手段，架构师能够快速确立清晰的系统边界，从而在宏观层面上对齐业务诉求与技术实现。

### 1.1 战略建模与上下文整合

复杂集成关系的梳理依赖于精确的上下文边界定义。通过制定防腐层、开放主机服务等交互契约，开发团队能够有效隔离核心子域与外部系统的耦合风险。以下技能专注于宏观业务领域的边界划分与系统集成映射。

| 技能名称               | 来源路径                                   | 来源资源库                   | 适用场景                                   |
| :--------------------- | :------------------------------------------- | :--------------------------- | :----------------------------------------- |
| `ddd-strategic-design` | `relative-skills/antigravity-awesome-skills` | `antigravity-awesome-skills` | 梳理复杂业务领域，规划微服务架构边界。     |
| `ddd-context-mapping`  | `relative-skills/antigravity-awesome-skills` | `antigravity-awesome-skills` | 遗留系统改造或多业务线系统集成设计。       |
| `ddd-planning`         | `relative-skills/claude-skill-registry`      | `claude-skill-registry`      | 需求分析阶段的业务专家与技术团队对齐认知。 |

- **`ddd-strategic-design` 深度分析**：
  该技能专注于领域子域（核心、支撑、通用）的提取与分类，并致力于打破单体架构的领域边界。其强制要求输出结构化的子域分类表、限界上下文目录、包含反模式术语的通用语言词汇表，并在代码实现前通过 ADR（架构决策记录）捕获上下文边界。它不仅关注技术划分，更强调团队所有权与限界上下文的对齐。
- **`ddd-context-mapping` 深度分析**：
  侧重于限界上下文之间的关系映射与集成契约设计。指导开发者识别依赖方向，并规划防腐层（ACL）、开放主机服务等集成模式。其核心输出包括上下文关系图、契约所有权矩阵以及已知的耦合风险与缓解计划，特别适用于防止外部域模型向核心域的泄漏。
- **`ddd-planning` 深度分析**：
  依托于庞大的综合性技能注册表生态，提供辅助性的事件风暴支持与需求拆解能力，协助团队在项目初期快速建立业务共识。

### 1.2 架构风格融合

领域模型的落地必须依托稳健的系统架构底座。将整洁架构或六边形架构的核心规则注入工程脚手架中，可以确保业务实体始终独立于数据库与外部接口框架。以下技能提供了从理论原则到脚手架生成的完整架构支撑。

| 技能名称             | 来源路径                        | 来源资源库        | 适用场景                                     |
| :------------------- | :-------------------------------- | :---------------- | :------------------------------------------- |
| `clean-architecture` | `relative-skills/wondelai-skills` | `wondelai-skills` | 构建高可测试性、易于演进的长期维护项目。     |
| `cleanddd-skills`    | `relative-skills/cleanddd-skills` | `cleanddd-skills` | 在 .NET 团队内部推行标准化领域驱动研发流程。 |

- **`clean-architecture` 深度分析**：
  基于 Robert C. Martin 的整洁架构理论，提供了一套严格的 0-10 分架构评分机制。它强制执行依赖倒置原则，确保内层（实体与用例）绝不依赖外层（框架与数据库）。技能内部详细定义了同心圆规则、组件内聚与耦合原则（REP, CCP, CRP 等），并运用谦卑对象（Humble Object）模式指导接口适配器的设计，彻底切断 ORM 或 Web 框架对业务逻辑的侵入。
- **`cleanddd-skills` 深度分析**：
  专为 .NET 平台量身定制的完整工作流技能集。它将研发过程解耦为四个连贯的子技能：需求拆解（生成结构化事件流）、分析建模（生成聚合/命令/查询/事件设计）、项目初始化（基于 `NetCorePal.Template` 生成骨架），以及代码实现。该技能严格规定了 C# 代码层面的 PascalCase 命名规范与文件放置约定，极大降低了 DDD 在 .NET 生态的落地门槛。

## 2. 战术落地与代码实现类

抽象的业务模型需要通过精确的代码结构予以具象化。深入代码细节层面的智能审查与生成工具，能够直接指导聚合根、值对象及领域服务的规范编写。

### 2.1 通用战术建模

面向对象设计原则的通用沉淀能够屏蔽底层编程语言的差异。跨技术栈的实体识别与仓储接口生成能力，保障了业务逻辑在领域层内部的高度内聚。以下技能致力于将业务模型映射为标准化的代码构造块。

| 技能名称               | 来源路径                        | 来源资源库        | 适用场景                             |
| :--------------------- | :-------------------------------- | :---------------- | :----------------------------------- |
| `domain-driven-design` | `relative-skills/wondelai-skills` | `wondelai-skills` | 核心业务逻辑复杂的后端系统底层建模。 |

- **`domain-driven-design` 深度分析**：
  强调“模型即代码”的核心理念，要求业务通用语言必须在类名、方法名及事件名中得到精确体现。该技能细致指导了实体（具备持久身份）与值对象（完全由属性定义、不可变）的区分，并确立了聚合根作为绝对一致性边界的设计规范。此外，它还规范了领域事件的时态命名与跨上下文解耦策略，配合仓储与工厂模式，确保业务逻辑免受基础设施层代码的污染。

### 2.2 特定技术栈专精

主流编程语言在工程实践中沉淀了截然不同的实现范式。深度绑定 Python 或 Java 等语言特性的专属指引，为开发者提供了符合原生框架生态的开箱即用体验。以下技能聚焦于特定后端技术栈的战术设计与测试规范。

| 技能名称                 | 来源路径                              | 来源资源库                       | 适用场景                                        |
| :----------------------- | :-------------------------------------- | :------------------------------- | :---------------------------------------------- |
| `arch-ddd`               | `relative-skills/aiee-team`             | `ai-enhanced-engineer/aiee-team` | Python 后端服务重构或新建。                     |
| `fastapi-ddd-guidelines` | `relative-skills/claude-skill-registry` | `claude-skill-registry`          | 基于 Python FastAPI 的微服务开发。              |
| `unit-test-ddd`          | `relative-skills/claude-skill-registry` | `claude-skill-registry`          | 提升 Spring Boot 领域模型核心逻辑的测试覆盖率。 |

- **`arch-ddd` 深度分析**：
  针对 Python 语言提出了四大战术支柱：纯粹的领域模型、仓储模式、服务层（用例编排与事务边界）以及工作单元模式（管理原子操作）。它还提供了一套基于领域所有权与数据所有权的服务划分决策框架，指导微服务架构下的功能归属。
- **`fastapi-ddd-guidelines` 深度分析**：
  深度结合 FastAPI 特性的架构指南。明确规定了 `domain/application/infrastructure/controller` 四层结构的依赖方向。其核心亮点在于整合了 Pydantic、SQLAlchemy (SQLModel) 及 Alembic 的使用规范，并强制要求通过 FastAPI 的 `Depends` 机制实现单请求单会话的管理策略。
- **`unit-test-ddd` 深度分析**：
  针对 Spring Boot 及 JUnit5+Mockito 环境的 DDD 单元测试规范。强制采用 AAA（Arrange-Act-Assert）模式与“Fail Fast”严格验证原则。它严禁在测试中省略对 DTO 字段、Mock 调用次数及异常副作用的断言，且绝对禁止服务层直接返回实体对象。其极度严苛的命名规则保障了测试套件作为活文档的价值。

## 3. 基础设施与智能代理框架类

高内聚与低耦合的设计哲学正在向人工智能工程化领域渗透。将限界上下文等概念引入智能代理的架构体系中，为处理多模态上下文与状态流转提供了稳健的基础设施。

### 3.1 代理工作流与底层内核

多步任务编排要求系统具备极强的状态管理能力。以聚合根形式封装代理执行状态与长效记忆，赋予了复杂智能模块高度的自治性与可扩展性。以下框架展示了如何将系统架构设计思想融入 AI 代理生态。

| 技能名称       | 来源路径                     | 来源资源库     | 适用场景                                     |
| :------------- | :----------------------------- | :------------- | :------------------------------------------- |
| `agentic-flow` | `relative-skills/agentic-flow` | `agentic-flow` | 研发多步骤、强上下文依赖的复杂代理系统。     |
| `solon-ai`     | `relative-skills/solon-ai`     | `solon-ai`     | 构建基于 Java 生态的高内聚智能技能生态组件。 |

- **`agentic-flow` 深度分析**：
  一个高度成熟的生产级 AI 代理编排框架。其内置了 SONA（自优化神经架构）与 AgentDB，支持超低延迟的模式学习与图神经网络（GNN）查询优化。该框架不仅实现了基于 Flash Attention 与 Hyperbolic Attention 的多代理协调共识机制（如拜占庭容错、Raft 协议），还包含了 66 个具备自学习能力的专业代理，展示了复杂智能体网络下极强的自治与协作能力。
- **`solon-ai` 深度分析**：
  基于 Java 生态的 LLM 与 RAG 应用开发框架。其架构设计体现了极强的扩展性与约束力，将大模型调用（ChatModel）、提示词工程、MCP 协议以及代理编排无缝融入 Solon 体系。它支持动态的技能准入机制与指令注入，并通过图驱动的编排模式，将代理的反思推理（ReAct）与团队协作（TeamAgent）转化为可观测、可治理的计算流图，是企业级 AI 业务流程编排的理想底座。

## 5. 调研结论

目前的领域驱动设计技能生态已形成从宏观战略、微观代码到 AI 原生基础设施的完整链路。战略规划类技能极大降低了领域专家与开发者的沟通成本并明确了系统边界；战术落地类技能深度结合了 Python、C#、Java 等语言特性，通过严格的架构规则与测试规范保障了充血模型的完美实现；而 `agentic-flow` 与 `solon-ai` 的出现，则标志着模块化、低耦合的架构思想已成功渗透进复杂多智能体协同系统的工程实践中。团队可根据项目所处阶段与技术栈偏好，精准引入上述技能库以大幅提升研发效能。
