# 01 — ddd-scope 产出（Blind Run）

> 输入：`00-fuzzy-prompt.md`（无 DDD 术语，无样例类名）。
> 本文件为 `ddd-scope` 在 blind run 下的模拟执行产出，**未参考** `reference/` 下任何真值材料。

## 问题陈述与价值陈述

- **问题陈述**：现有"邮件 + Excel + 零散系统"的国际海运流程，使从客户提出托运需求到签收的端到端协作不可追踪、不可监控、不可干预，导致下单周期长、作业数据混乱、异常发现滞后、客户自助查询缺位。
- **价值陈述**：构建一个以"一票货物的全生命周期"为中心的统一系统，使订舱、港口作业、异常重规划、客户查询在同一事实基础上协同，显著缩短下单响应时间，并将异常从"客户来电暴露"转为"系统主动识别"。

## 目标 / 非目标

### 目标

1. 客户在线提交托运需求（起点、终点、最晚到达时间），系统返回可选方案列表，客户选择即完成下单。
2. 港口作业方可通过 Web/API/文件多通道登记作业事实，系统对重复提交与非法数据能自动识别。
3. 系统主动识别"货物走错"的异常，并支持基于当前位置重新规划到目的地的方案，优先保住承诺的最晚到达时间。
4. 客户可自助查询货物当前位置、状态、下一步预期动作与预计到达时间。
5. 与外部航线数据提供方保持松耦合：外部字段不得直接出现在核心模型内；外部变更不会击穿核心流程。

### 非目标（显式声明不做）

- **不做计费与财务**：计价、应收、开票、对账在本期范围之外。
- **不做客户 CRM**：客户联系方式、信用档案、历史对账不纳入本系统。
- **不做船公司内部调度**：不为船公司安排船期班次。
- **不做仓储管理**：仓库内部摆放、盘点不纳入本系统。

## 约束与假设

| 约束 / 假设                                       | 可验证性   | 验证方式                                     |
| :------------------------------------------------ | :--------- | :------------------------------------------- |
| 外部港口作业数据可能延迟数小时至数天到达          | 可验证     | 对现有邮件/对接系统抽样统计到达延迟分布      |
| 同一港口作业事实可能被重复提交                    | 可验证     | 抽样历史数据的重复率统计；观察导入日志       |
| 外部航线提供方接口随时可能变化                    | 可验证     | 调阅外部提供方过往 12 个月接口变更记录       |
| 一票货物生命周期通常 2–6 周                       | 可验证     | 抽样历史订单的下单到签收时间分布             |
| 货物在途允许改目的地、改航线                      | 部分可验证 | 抽样历史变更记录；与业务方确认允许的变更类型 |
| 峰值每天下单 5000 票、作业事件 50 万条、QPS ≈ 200 | 可验证     | 根据历史交易量推算与日志回放                 |
| 三支团队（订舱/作业数据对接/客户前端）相对独立    | 可验证     | 查看组织结构图与实际沟通频度                 |
| 外部航线数据提供方关系在本期与可见未来保持稳定    | 不可验证   | 业务方一次性确认，列入风险                   |
| 本期不承担计费、CRM、船公司调度、仓储             | 可验证     | 明确纳入验收清单与边界说明                   |

## 术语种子清单

| 术语                    | 定义候选                                                           | 歧义点                                         | 所属场景        |
| :---------------------- | :----------------------------------------------------------------- | :--------------------------------------------- | :-------------- |
| 托运需求                | 客户提出的"把货从 A 运到 B，不晚于 T"的愿望                        | 与"订单"是否同义？客户改需求是否算新需求？     | 下单            |
| 方案                    | 一条可行的"从起点到终点"的运输安排                                 | 是一次调用的临时结果，还是一条可持久化的实体？ | 下单 / 重规划   |
| 订单 / 一票货物         | 客户确认方案后产生的"一次实际运输承诺"                             | "订单"与"一票货物"是否 1:1？                   | 全流程          |
| 起点 / 终点             | 客户要求的装货港与交付港                                           | 是否只能是港口？可否为门到门？                 | 下单            |
| 最晚到达时间            | 客户希望货物不晚于该时间交付                                       | 是硬约束还是软约束？越界是否算违约？           | 下单 / 异常     |
| 作业事实                | 某港口在某时间发生的具体动作（收货、装船、卸船、到港、提货、转运） | 类型集合是否封闭？是否允许自定义？             | 港口作业        |
| 作业登记                | 把作业事实写入系统的动作                                           | 由谁有权登记？外部方与内部方权限是否不同？     | 港口作业        |
| 重复登记                | 同一作业事实被多次提交                                             | 判重依据是哪几个字段的组合？                   | 港口作业        |
| 非法登记                | 字段缺失或业务规则上不可能的作业                                   | 非法定义是否与作业类型相关？                   | 港口作业        |
| 航线 / 航段             | 一次运输涉及的一段或多段船期                                       | "航线"是客户视角还是作业视角？                 | 下单 / 重规划   |
| 外部航线提供方          | 提供可行方案数据的第三方系统                                       | 是数据源，还是"决策者"？                       | 下单 / 重规划   |
| 走错 / 错卸             | 货物到达了本不应到达的港口                                         | 判定依据是"应去的地方" vs 实际；谁来判？       | 异常识别        |
| 重新规划                | 基于当前位置重新生成到目的地的方案                                 | 是系统自动发起还是人工发起？                   | 异常            |
| 当前位置                | 货物此刻所在的物理位置                                             | 时延：最后一条作业事实是否等同于"当前"？       | 客户查询 / 异常 |
| 下一步预期动作          | 根据已有方案，接下来应发生什么                                     | 如何在方案变更时保持一致？                     | 客户查询        |
| 预计到达时间            | 对方案剩余部分的时间估算                                           | 谁负责算？作业延迟是否实时反馈？               | 客户查询        |
| 客户                    | 提出托运需求并接收交付的外部主体                                   | 是否需要与 CRM 对接？本期明确不做              | 全流程          |
| 港口作业方              | 在某港口执行作业并登记事实的角色                                   | 内部员工与外部合作方权限差异                   | 港口作业        |
| 订舱员                  | 协助客户挑选方案并确认下单的内部角色                               | 自动化后角色职责如何收窄？                     | 下单            |
| 防腐层 / 翻译层（隐式） | 隔离外部航线提供方字段的一层翻译                                   | 在下单与重规划两处都需要吗？                   | 集成            |

（合计 20 条，均标注歧义点与场景。）

## 风险清单

| 风险                                                       | 影响                                 | 触发条件                       | 缓解建议                                           |
| :--------------------------------------------------------- | :----------------------------------- | :----------------------------- | :------------------------------------------------- |
| **业务**：三支团队独立导致术语不一致                       | 模型边界模糊、接口漂移               | 订舱/作业/前端各自发明术语     | 第一轮统一术语表；每个边界上强制双向翻译           |
| **业务**：非目标被隐性突破（如前端要求看价格）             | 范围蔓延、团队被动拒绝               | 客户/前端临时需求              | 将非目标纳入验收签署；对越界需求走变更评审         |
| **集成**：外部航线提供方接口变更                           | 下单与重规划不可用                   | 对方版本升级或字段改名         | 防腐层隔离；合同测试；自动兜底降级                 |
| **集成**：港口作业数据迟到、重复、字段不规范               | 客户查询不准、异常误报               | 外部方以邮件/文件/异步推送提交 | 异步吸收 + 去重键 + 校验失败入隔离区               |
| **一致性**：作业事实登记的"发生时间"与"到达系统时间"不一致 | 状态推导错乱                         | 外部方延迟数小时到数天         | 明确以"发生时间"驱动状态推导；"系统到达时间"仅审计 |
| **一致性**：货物状态由多源事实推导，判定口径不统一         | "货走到哪了"客服口径与系统口径不一致 | 多系统并存期                   | 确定权威推导规则；禁止状态被外部直接覆盖           |
| **一致性**：异常识别滞后                                   | 客户已感知错误，系统才告警           | 错卸、误装、晚到               | 将异常识别绑定到作业登记事件的即时处理             |
| **交付**：50 万事件/日峰值，判重与状态推导成本高           | 登记入库延迟，客户查询慢             | 峰值时段                       | 异步化 + 分区；先幂等写入、再派生视图              |
| **交付**：三团队独立节奏，接口集成反复返工                 | 排期拖延                             | 并行开发未锁定契约             | 尽早冻结边界与契约；里程碑合同测试                 |
| **交付**：下单体验期望过高（秒级返回方案）                 | 达不到预期导致复购率下降             | 外部提供方响应慢               | 明确方案查询为"准实时"；允许降级与缓存             |

（覆盖业务 / 集成 / 一致性 / 交付四类。）
