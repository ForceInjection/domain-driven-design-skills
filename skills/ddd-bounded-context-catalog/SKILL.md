# Bounded Context Catalog

## 使用时机

- 需要把“能力/子域”转化为可治理的系统边界与团队边界。
- 需要为微服务拆分、模块化单体或组织协作提供清晰边界。

## 输入要求

- 子域分类表与核心域声明（来自阶段 2）。
- 事件流表与热点标注（来自阶段 1）。
- 组织信息：团队边界、交付节奏（如已知）。

## 流程

1. 将能力按一致性与语言边界聚类，提出上下文候选集合。  
2. 为每个上下文定义：业务职责、核心概念、主要事件、数据所有权。  
3. 明确边界规则：哪些概念只在本上下文有效，哪些概念必须翻译。  
4. 形成所有权：责任团队、决策者、对外契约 Owner。  
5. 输出边界 ADR：边界选择理由、权衡、风险、替代方案。  
6. 生成词汇表骨架：上下文内术语与跨上下文同名词对照。

## 输出

| 工件 | 结构要求 |
| :--- | :--- |
| 限界上下文目录 | 表格：上下文、职责、核心概念、主要事件、数据所有权、团队 |
| 边界 ADR 列表 | 每条包含：决策、理由、权衡、风险、替代 |
| 词汇表骨架 | 表格：术语、上下文内定义、跨上下文冲突、翻译策略 |

## 校验清单

- [ ] 每个上下文都有清晰职责与“非职责”
- [ ] 数据所有权不冲突，跨上下文访问通过契约或翻译
- [ ] 每个边界都有至少 1 个明确权衡点与风险点

## 常见陷阱

- 把技术分层当作上下文边界，导致语言边界缺失。
- “共享数据库”掩盖了边界冲突，后续演进成本巨大。

## 示例

```text
使用 @ddd-bounded-context-catalog 将子域分类表收敛为限界上下文目录：
输出上下文职责/数据所有权/团队所有权、边界 ADR 与词汇表骨架。
```
