# DDD Skill 快速上手（Quickstart）

> 🌐 English version: [English](ddd-quickstart.en.md)

---

> 本文回答三个问题：这套 Skill 是什么？在哪里运行？怎么从 0 到 1 完成一次领域建模？
> 目标读者：第一次接触本仓库、想立刻上手试一下的开发者。

## 1. 这套 Skill 是什么？

- **不是可安装的软件**，而是给 AI 助手（支持 Agent Skill 的对话环境）的**指令包**。
- 每个 Skill 是一份 `SKILL.md`：告诉 AI 在某个建模环节"按什么流程、产出什么格式的工件"。
- 9 个 Skill 组成 **5 阶段流水线**：范围收敛（I）→ 战略设计（II）→ 战术设计（III）→ 模型验证（IV）→ OpenSpec 规范衔接（V）。每个阶段的工件是下一个阶段的输入。

```text
@ddd-scope → @ddd-discover → @ddd-subdomains → @ddd-contexts → @ddd-context-map
   → @ddd-aggregates → @ddd-domain-interactions → @ddd-model-review → @ddd-openspec-bridge
```

## 2. 前置准备

| 需要                        | 说明                                                          |
| :-------------------------- | :------------------------------------------------------------ |
| 支持 Agent Skill 的 AI 工具 | 如 Claude Code、Qoder 等支持 `@skill` 语法或 Skill 目录的环境 |
| Git                         | 克隆本仓库                                                    |
| 运行环境                    | **无**——本仓库是纯文档/规范仓库，不需要安装依赖或启动服务     |

克隆仓库：

```bash
git clone --recurse-submodules https://github.com/ForceInjection/domain-driven-design-skills.git
```

获取 Skill 的方式（二选一）：

- **方式 A（推荐）**：把 `skills/ddd-*/` 目录复制到你的 AI 工具的 Skill 目录（如 Claude Code 的 `~/.claude/skills/` 或项目 `.claude/skills/`），之后可直接 `@ddd-*` 引用。
- **方式 B**：不复制，直接在会话中把 `skills/<skill>/SKILL.md` 的内容作为指令粘贴给 AI，再把业务描述作为输入。

## 3. 启动前：访谈与需求梳理（关键一步）

`@ddd-scope` 的输入是一段**业务描述**，而业务描述不是凭空来的——它来自对业务方的**访谈**与**需求梳理**。建模质量的上限取决于你对业务的理解，所以这是启动技能之前的关键一步。

### 3.1 访谈谁

| 访谈对象                           | 能提供什么                             |
| :--------------------------------- | :------------------------------------- |
| 业务方（领域专家）                 | 业务目标、流程全貌、规则与例外         |
| 一线操作者（客服 / 核保 / 理赔等） | 实际怎么做事、什么情况会出错、系统痛点 |
| 管理层                             | 目标与约束（合规、预算、节奏）         |
| 系统负责人（如有现状系统）         | 现有系统边界、数据来源                 |

### 3.2 问什么（访谈提纲）

- **业务目标**：你们希望解决什么问题？衡量成功的指标是什么？
- **核心流程**：一件事从开始到结束怎么走？（请业务方完整讲一遍）
- **角色**：谁参与？各做什么？
- **异常与例外**：什么情况会出错？出错后怎么处理？
- **术语**：你们管这些事物叫什么？（记录业务方原话——这些词很可能是建模的通用语言种子）

### 3.3 怎么整理成业务描述

访谈记录 → 需求梳理 → 一段业务描述：

1. 目标与非目标（做什么 / 明确不做什么）
2. 主流程 + 异常情况（至少想清楚 2–3 种出错场景）
3. 角色清单
4. 业务方术语表（原话）
5. 约束与风险

整理成 3–5 句话的问题描述（现状痛点 + 期望目标），就是 `@ddd-scope` 的输入。

> 如果你本人就是业务方：用自己的话直接讲给 AI 听即可，可跳过访谈。

## 4. 第一个对话：`@ddd-scope`

给 AI 你梳理出的业务描述（来自步骤 3，允许仍很模糊、非结构化）：

```text
@ddd-scope
业务描述：我们的订单售后流程非常混乱，跨系统协同困难，客户投诉响应慢。
请帮我收敛为 DDD 建模输入：输出问题陈述、目标/非目标、约束与假设、术语种子、风险清单。
```

AI 将产出一份结构化工件：问题陈述与价值陈述、目标/非目标、约束与假设表、术语种子清单（≥10 个）、风险清单。

## 5. 工件传递：`@ddd-discover` → … → `@ddd-model-review`

把上一个 Skill 的产出粘贴给下一个 Skill：

```text
@ddd-discover
基于以下 scope 输出，帮我做领域发现：
[粘贴上一步产出]
请输出事件流表（主路径 + 异常分支）、命令/事件候选、热点标注与歧义清单。
```

依次走完 8 个建模 Skill（阶段 I–IV）。**不必一次跑完**：可以从任何阶段进入（全新项目 / 已有系统 / 局部深化 / 模型体检，见 [README](../README.md) 的入口选择表），也可以随时中断，下次用已有工件继续。

## 6. 完成后你会得到什么？

走完流水线后，你拥有整套**结构化工件**：

| 阶段     | 产出示例                                                                                            |
| :------- | :-------------------------------------------------------------------------------------------------- |
| I 发现   | 问题陈述、事件流表（主路径 + 异常分支）、术语种子                                                   |
| II 战略  | 子域分类（Core/Supporting/Generic）、限界上下文目录、通用语言词汇表、边界 ADR、上下文映射与集成模式 |
| III 战术 | 聚合目录与不变量表、实体/值对象清单、领域事件目录、领域服务、仓储接口、工厂                         |
| IV 验证  | 分维度评分、问题清单、回溯判定（Ready / Not Ready）                                                 |

想看完整成品长什么样？`validation-cases/` 下有两个端到端案例：

- [cargo-validation](../validation-cases/cargo-validation/)：物流领域，有权威参考实现对标（得分 85.8%），含全部 01–08 工件
- [insurance-validation](../validation-cases/insurance-validation/)：保险承保与理赔，无参考实现（专家评审 90.9%），含 01–09 全链工件（09 为 OpenSpec 变更集）

## 7. 衔接工程实现：`@ddd-openspec-bridge`（阶段 V）

建模产物最终通过阶段 V 转成可执行的工程规范：

```text
@ddd-openspec-bridge
根据已完成的建模产出，生成 OpenSpec 变更集规范：
[粘贴 04–07 的上下文、聚合、事件工件]
请输出 proposal.md、design.md 以及 specs/ 下的 spec.md（Requirement + Scenario）。
```

产出 OpenSpec 规范（Requirement + Scenario，Gherkin 格式）后，交给开发者或下游 AI 工具按规范实现代码——**本仓库不生成业务代码**，建模与规范衔接是它的边界。

## 8. FAQ

| 问题                          | 回答                                                                                          |
| :---------------------------- | :-------------------------------------------------------------------------------------------- |
| Skill 在哪里运行？            | 在 AI 助手环境中，不是独立程序；用 `@skill-name` 语法调用                                     |
| 需要写代码吗？                | 不需要。本仓库聚焦领域建模与规范衔接（OpenSpec），代码实现由开发者或下游 AI 完成              |
| 产出的一堆表格有什么用？      | 它们是下一个 Skill 的输入（保证工件可衔接），也是 OpenSpec 规范的来源                         |
| 能跳过某些阶段吗？            | 可以。见 [README](../README.md) "入口选择与调用方式"，按场景选入口                            |
| 每个 Skill 的输出要求是什么？ | 各 Skill 的 `SKILL.md` 有输出表、校验清单与回溯触发条件，AI 会遵循                            |
| 模型质量怎么保证？            | 阶段 IV `ddd-model-review` 按维度评分并触发回溯（如不变量表达率 < 60% 回到 `ddd-aggregates`） |
| 在哪看完整示例？              | `validation-cases/` 两个案例的 01–09 工件即完整走查                                           |
