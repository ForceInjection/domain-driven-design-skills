# Context Map & Contracts

## 使用时机

- 系统存在多个限界上下文，需要明确上下游关系、契约所有权与翻译策略。
- 遗留系统迁移或多业务线集成，担心外部模型污染核心域。

## 输入要求

- 限界上下文目录（来自阶段 2）。
- 事件流热点标注（跨边界点、强一致性点）。
- 现有接口/消息/数据交换方式（如有）。

## 流程

1. 列出所有上下文对（Context Pair），标注依赖方向与数据/事件流向。  
2. 为每个上下文对选择关系模式：ACL、OHS、PL、Shared Kernel 等，并给出理由。  
3. 定义翻译规则：输入翻译、输出翻译、语义差异处理、字段映射。  
4. 明确契约所有权与变更流程：谁定义、谁发布、谁升级、谁兼容。  
5. 梳理失败模式：超时、降级、幂等、重试、补偿、数据延迟。  
6. 制定版本策略：兼容窗口、弃用策略、契约测试与发布节奏。  

## 输出

| 工件 | 结构要求 |
| :--- | :--- |
| 上下文关系矩阵 | 表格：上游、下游、模式、数据/事件、风险 |
| 契约所有权矩阵 | 表格：契约、Owner、消费者、变更流程、发布策略 |
| 翻译与 ACL 决策 | 表格：对象/事件、翻译规则、差异说明、实现位置 |
| 失败模式与缓解 | 表格：失败模式、影响、检测、缓解、补偿 |
| 版本策略 | 列表：版本号规则、兼容窗口、弃用策略、契约测试 |

## 校验清单

- [ ] 所有跨上下文交互都有明确模式与所有权
- [ ] 核心域对外输入均通过 ACL 或等价翻译边界
- [ ] 至少列出 5 类失败模式并给出可执行缓解

## 常见陷阱

- Shared Kernel 失控，变成跨团队强耦合共享模型。
- 未定义契约变更流程，导致消费者被动跟随与频繁事故。

## 示例

```text
使用 @ddd-context-map-contracts 为“结算”与“订单/库存/风控”建立上下文映射：
输出关系矩阵、契约所有权、ACL 翻译策略、失败模式与版本策略。
```
