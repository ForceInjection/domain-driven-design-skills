# Subdomain Classification

## 使用时机

- 需要决定“哪些能力值得深度建模”，避免对通用能力过度设计。
- 需要为组织结构、团队边界与投资优先级提供依据。

## 输入要求

- 事件流/命令/术语候选（来自阶段 1）。
- 当前系统能力清单或模块清单（如有）。
- 商业差异化点、竞争优势假设（如有）。

## 流程

1. 从事件流中提取能力集合（Capability），去重并合并同义能力。  
2. 为每个能力补齐：业务价值、复杂度、变化频率、对外依赖。  
3. 按 DDD 子域类型分类：核心子域/支撑子域/通用子域。  
4. 形成核心域声明：为什么它是核心、衡量指标、长期演进方向。  
5. 给出团队所有权建议：按语言边界与一致性边界对齐，并标注跨团队协作点。  
6. 输出下一步限界上下文划分的候选边界线索。

## 输出

| 工件 | 结构要求 |
| :--- | :--- |
| 能力清单 | 表格：能力、解释、关键事件、上下游依赖 |
| 子域分类表 | 表格：能力、子域类型、理由、建议投入 |
| 核心域声明 | 1 页内：价值、边界、指标、风险 |
| 所有权建议 | 表格：能力/子域、建议团队、依赖关系、协作方式 |

## 校验清单

- [ ] 每个能力都有分类理由，且能被业务与技术共同接受
- [ ] 核心域声明包含可衡量指标
- [ ] 至少识别 3 个跨团队协作点并给出缓解方式

## 常见陷阱

- 把“技术平台能力”误判为核心域，导致核心域被稀释。
- 分类只看主观偏好，缺少商业指标与变化频率支撑。

## 示例

```text
使用 @ddd-subdomain-classification 基于事件流对我们的“营销、订单、结算、库存、风控”进行子域分类：
输出子域分类表、核心域声明与团队所有权建议。
```
