# Dependency Rule Check

## 使用时机

- 现有项目存在“框架侵入业务”、“ORM 泄漏到领域层”、“控制器承载业务逻辑”等问题。
- 需要给出可执行的重构路径，并用评分机制跟踪改进效果。

## 输入要求

- 项目目录结构与主要模块说明。
- 关键用例列表与入口（HTTP/CLI/消息消费）。
- 现有依赖/模块边界约束（如有）。

## 流程

1. 定义目标分层模型：实体/用例/适配器/框架（可按项目调整）。  
2. 扫描依赖方向：列出跨层引用与循环依赖候选。  
3. 定位典型违规：ORM/框架类型出现在领域层、领域对象依赖外部 SDK、用例依赖控制器。  
4. 给出修复建议：引入接口边界、DTO 映射、依赖倒置、组合根（composition root）。  
5. 输出评分：0-10 分，并列出达到 10/10 的必要改造清单。  
6. 输出落地路线：按风险与收益排序，给出最小可行重构切片。  

## 输出

| 工件 | 结构要求 |
| :--- | :--- |
| 违规依赖清单 | 表格：位置、违规类型、影响、修复建议 |
| 评分报告 | 当前分数、主要扣分项、达标路径 |
| 重构切片路线 | 表格：切片、范围、风险、回滚策略、验收方式 |

## 校验清单

- [ ] 能清楚指出至少 5 类依赖违规或确认不存在
- [ ] 每条违规都有“如何修复”的可执行步骤
- [ ] 评分口径一致，复测可重复

## 常见陷阱

- 一次性大重构，缺少切片与回滚策略。
- 只改目录不改依赖方向，问题以新形态复现。

## 示例

```text
使用 @ddd-architecture-dependency-rule-check 体检当前项目的 DDD/整洁架构合规性：
输出违规依赖清单、0-10 评分与可切片的重构路线。
```
